# 执行资源规模台账（DRSC）

> **为什么不是六面**：`dsh-prime-memory` 的六面台账适用于「有模型推理、有子进程、有前后台队列」的插件。DRSC 只有**两面**真正成立（F1 分批/预算、F6 留痕），外加**两个它自己专有的规模面**（新鲜度承诺、投影库体积）和**一条已知债**（单会话投影无上界）。
> **真值源纪律**：值以代码为准；改旋钮时同步本表。
> **姊妹篇**：宿主侧限制见两个知识库仓的 `electron-host-constraints*.md`；六面方法论见 skill 仓 `dsh-plugin-dev/references/execution-scale-control.md`。

---

## 0. 六面里哪几面成立

| 面 | 是否成立 | 说明 |
|---|---|---|
| **F1 分批 / 预算** | ✅ | 目录发现上限 + 单轮时间预算 + 断点游标 |
| **F2 子进程隔离** | ❌ | 零原生依赖：`node:sqlite`（内置）+ 自带解码叶子；无 CRAN/ABI 面 |
| **F3 崩溃自愈** | ❌ | 没有子进程可崩；`syncing` 旗标防重入即可 |
| **F4 压力控制（熔断/退避）** | ❌ | 不调用 LLM/远端服务，没有「慢依赖」这回事 |
| **F5 队列与优先级** | ❌ | 无前台请求队列：同步是后台 interval，查询面只读 |
| **F6 预算留痕** | ✅ | 每轮 `budgetExhausted` / `deferred` / `durationMs` / `basis` |

> 一句话：**DRSC 的规模问题不是「处理得多贵」，而是「一轮能不能在两次触发之间跑完」。**

## 1. F1：分批与预算

| 机制 | 值 / 行为 | 为什么 |
|---|---|---|
| 目录发现上限 | `DISCOVERY_LIMIT = 5000` | walk 兜底，防异常目录树拖死主线程 |
| 单轮时间预算 | `DEFAULT_SYNC_BUDGET_MS = 20_000`（< interval 30s） | 一轮必须落在两次触发之间，否则轮轮相撞（撞旗标直接 busy = 什么都没做） |
| 预算的作用面 | **只拦「尚未开始的会话」** | `syncOne` 里 `readFileSync` / decode / project / `replaceSession` 全是不可中断的同步段，预算拦不住它们 |
| 第一个会话放行 | 恒放行 | 预算小于单会话耗时时，否则会出现「零进度轮」——游标不前进，是另一种活锁 |
| 断点游标 | `resumeCursor`（内存态，重启归零） | 不轮转则预算永远在 walk 头部耗尽，尾部会话永远轮不到，而头部每轮 stat-skip 全命中——表面「同步一直正常」 |
| 不完整轮禁剪枝 | 预算中断 / 发现截断 / `sessions` 根缺失 → 不动手删投影 | 「这轮没扫到」≠「宿主已删除」；误删不可逆，宁留陈旧行 |
| 轮尾水位 | 预算中断**也写** blocks 水位 | 跳过它会让下一轮把「自己没扫完」误判成「字典被驱逐」而全量重投 |

**F1 的不变量**：一次 `syncAll` 必须能在有限时间内返回，且返回时**要么覆盖全部、要么如实报告还剩多少**；「看起来跑过了」不算。

## 2. F6：留痕

| 留痕 | 位置 | 回答什么 |
|---|---|---|
| `totalDiscovered` | `SyncResult` / `last_sync` | 这一轮看到多少个会话（全集，不是处理数） |
| `budgetExhausted` | 同上 | 这一轮是不是**不完整轮** |
| `deferred` | 同上 | 还剩多少没处理（0 = 扫完） |
| `basis` | 同上 | 长度口径是 `ds-token`（精确词表）还是 `chars/4`（资产缺席降级） |
| `durationMs` | 同上 | 这一轮真实耗时（预算调参的唯一依据） |
| `syncing` | `op=status` 顶层 | 现在是否真在跑（不是上一轮结果） |
| `softSkips` / `failures` / `pruned` | `SyncResult` | 跳过了什么、坏了什么、剪了什么 |

**消费方契约**：`syncing=false` **不等于**扫完。判落定要 `syncing === false && deferred === 0`。旧版无 `deferred` 字段，按 0 处理（行为与旧版一致）。

## 3. 专有面 A：新鲜度承诺 vs 实际耗时

| 项 | 数 |
|---|---|
| 承诺（steward 二期要的） | 新鲜度 ≤ 1 分钟 |
| interval 缺省 | 30s |
| 单会话成本 | ≈0.56s（90 会话 / 70s 首轮全量，2026-11 实测） |
| 90 会话一轮（旧，无预算） | **70s > interval 30s ⇒ 必然轮轮相撞** |
| 90 会话一轮（新，20s 预算） | 约 36 个/轮 ⇒ 建完一遍约 3 轮 ≈ 60–90s |
| 稳态（多数 stat 命中） | 远低于预算，几乎不触发 |

**裁决**：冷启动/大批新增时「≤1 分钟建完全部」**不成立**，这是故意的取舍——旧行为虽然「一轮扫完」，但它把主线程按了 70s，且期间 interval 触发全部 busy。现在的形状是**恒定 20s 工作片 + 可观测的剩余量**。

> 不要为了「一轮扫完」把预算调大：调大只会让单次占用变长并继续撞 interval。真要提速得降单会话成本（见 §5）。

## 4. 专有面 B：投影库体积

| 项 | 数 |
|---|---|
| 实测倍率 | ≈2.5×（未归档 JSONL 压缩域 6.28MB → 库约 15.5MB） |
| 组成 | blocks 明文 4.5MB + search_text 增量 2.9MB + fts 副本 4.3MB + 索引 2.5MB |
| 近似理论地板 | 已接近：字块共享（`blocks` 按 hash 去重）压掉了重复正文 |

**边界**：倍率随会话冗余度变化，不是常数；`fts` 是独立副本，想省只能牺牲检索面。

## 5. 已知债

| 债 | 影响 | 为什么现在不修 |
|---|---|---|
| **单会话投影无上界、不可中断** | 一个几万事件的会话单次 `replaceSession`（事务内 DELETE+INSERT）可能吃满整轮预算 | 要治需在 `projection.ts` 分块 + 把「全量重写」改成增量 upsert，会触及「幂等可重放」契约 |
| **剪枝会推迟** | 宿主删掉的会话，投影要等到某个完整轮才清 | 宁可留陈旧行也不误删（不完整轮禁剪枝是刻意的） |
| **`sessions` 汇总的 `title` 无脱敏臂** | `redact` 只落在 `session` / `search` 两条路径 | 要加需在 summaries 缓存层再做一份 redacted 投影，成本高于收益（消费方只用它做定位） |
| **游标是内存态** | 重启后从头开始 | 它是调度优化，不是事实源；持久化会引入新的 schema 与失效面 |

## 6. 面间冲突

| # | 冲突 | 裁决 |
|---|---|---|
| 1 | 预算小 → 轮次多、新鲜度退化 vs 预算大 → 单次占用长、撞 interval | 预算必须 < interval；新鲜度靠**稳态 stat 命中**而不是靠单轮跑满 |
| 2 | 不完整轮禁剪枝 vs 陈旧行留存 | 留陈旧行（可逆）优先于误删（不可逆） |
| 3 | 游标前进 vs 第一个会话放行 | 放行：零进度轮比慢一点更糟（游标永不前进 = 活锁） |
| 4 | 观测字段只增 vs `SyncResult` 类型稳定 | 加法可接受；`budgetExhausted`/`deferred` 设为必填是为了让「忘了看」不可能发生 |

## 7. 复跑与观测

```bash
npm run check                 # typecheck → lint → test → build → smoke
# smoke 会打印真实库的同步形状，预算是否生效直接看这一行：
#   boot sync partial: updated=36 skipped=0 deferred=54 basis=ds-token 20256ms

DSH_REFERENCE_SESSION_COLLECTOR_SYNC_BUDGET_MS=0      # 不限（首轮建全库排障用）
DSH_REFERENCE_SESSION_COLLECTOR_SYNC_BUDGET_MS=5000   # 压到 5s 看游标是否在推进
DSH_REFERENCE_SESSION_COLLECTOR_SYNC_INTERVAL_MS=0    # 关掉 interval，纯手动
```

**调参 SOP**：改预算前后各跑一次 smoke，对比 `updated` / `deferred` / `durationMs` 三列；只看 `updated` 会把「预算调大」误读成「同步变快」。
